# H1 · Crear una solicitud

- **Issue:** —
- **Estado:** Aprobada
- **Aprobada por:** Tomás Fermoso · 17/11/2026

## Historia
Como usuario quiero crear una solicitud con título y descripción para registrar una petición.

## Alcance
- Incluido: crear solicitudes mediante `POST /requests`, validar y recortar título y descripción, e ignorar campos extra del cuerpo. La API genera el identificador, el estado inicial y la fecha de creación.
- Fuera de alcance: consultar, listar o modificar solicitudes; persistencia fuera de memoria; reglas de negocio adicionales sobre la descripción.

## Criterios de aceptación
1. **Dado** un cuerpo válido con `title` y `description` **cuando** se envía a `POST /requests` **entonces** la API devuelve 201 y un objeto con `id`, `title`, `description`, `status: "open"` y `created_at`.
2. **Dado** un título con espacios al principio o al final y contenido no vacío **cuando** se envía a `POST /requests` **entonces** la API recorta esos espacios antes de guardar y devuelve el título recortado.
3. **Dada** una descripción con espacios al principio o al final y contenido no vacío **cuando** se envía a `POST /requests` **entonces** la API recorta esos espacios antes de guardar y devuelve la descripción recortada.
4. **Dado** un cuerpo sin `title`, con `title` que no sea texto, vacío o compuesto solo por espacios **cuando** se envía a `POST /requests` **entonces** la API devuelve 400 con un cuerpo JSON de la forma `{"error": "..."}`.
5. **Dado** un título que, tras recortarlo, tiene entre 1 y 100 caracteres **cuando** se envía a `POST /requests` **entonces** se acepta; un título de exactamente 100 caracteres tras recortarlo es válido y uno de 101 se rechaza con 400 y un cuerpo JSON de la forma `{"error": "..."}`.
6. **Dado** un cuerpo sin `description`, con `description` que no sea texto, vacío o compuesto solo por espacios **cuando** se envía a `POST /requests` **entonces** la API devuelve 400 con un cuerpo JSON de la forma `{"error": "..."}`.
7. **Dada** una descripción que, tras recortarla, tiene entre 1 y 1000 caracteres **cuando** se envía a `POST /requests` **entonces** se acepta; una descripción de exactamente 1000 caracteres tras recortarla es válida y una de 1001 se rechaza con 400 y un cuerpo JSON de la forma `{"error": "..."}`.
8. **Dado** un cuerpo válido que incluye campos extra **cuando** se envía a `POST /requests` **entonces** la API ignora esos campos, devuelve 201 y no los incluye en el objeto de respuesta.
9. **Dadas** dos solicitudes válidas **cuando** se crean por separado **entonces** cada respuesta contiene un `id` no vacío y distinto, y un `created_at` que puede interpretarse como fecha y hora ISO 8601 con zona horaria.
10. **Dado** un cuerpo JSON malformado **cuando** se envía a `POST /requests` **entonces** la API devuelve 400 con un cuerpo JSON de la forma `{"error": "..."}`.

## Contrato de la API
| Método | Ruta | Cuerpo | Respuesta correcta | Errores |
|---|---|---|---|---|
| POST | `/requests` | Objeto JSON con `title` y `description`, ambos obligatorios y de tipo texto. Se recortan los espacios al principio y al final antes de validar y guardar. Tras el recorte, `title` debe tener entre 1 y 100 caracteres y `description` entre 1 y 1000. Los campos extra se ignoran. | `201 Created`; objeto con `id` (cadena no vacía y generada por la API), `title` y `description` ya recortados, `status` (`"open"`) y `created_at` (fecha y hora ISO 8601 con zona horaria). Los campos extra del cuerpo no aparecen en la respuesta. | `400 Bad Request` para JSON malformado, campos ausentes, valores que no sean texto o valores vacíos o fuera de los límites tras recortarlos; cuerpo `{"error": "<mensaje>"}`. El texto exacto del mensaje no forma parte del contrato. |

## Casos límite y dudas abiertas
- `title` y `description` son obligatorios; ambos deben ser texto y no pueden quedar vacíos después del recorte.
- Los límites se aplican después del recorte: título de 1 a 100 caracteres inclusive y descripción de 1 a 1000 caracteres inclusive.
- Los espacios al principio y al final se eliminan de ambos campos antes de validar y guardar; los espacios interiores se conservan.
- Los campos extra del cuerpo se ignoran y no se reflejan en la respuesta.
- Los errores de validación y de JSON malformado usan el formato común `{"error": "..."}` y estado 400 ya definido para la aplicación.
- El identificador no tiene un formato específico fijado; se comprueba que no esté vacío y que no se repita entre dos creaciones.
- La fecha debe incluir zona horaria; no se fija una zona concreta ni se compara con una hora exacta.
- El repositorio en memoria debe poder vaciarse entre tests, según la arquitectura.
- No quedan dudas abiertas de producto para esta historia.
